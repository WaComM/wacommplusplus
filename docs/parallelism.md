# Parallel execution

Enable one or more optional backends at configure time, for example `-DUSE_OMP=ON` or `-DUSE_MPI=ON`. MPI and EMPI are mutually exclusive. Concentration counts each living particle in the rho cell nearest to its fractional position. With OpenMP, every thread owns a range of cells and is the only writer of those counts, so no atomic update is needed. Each thread first finds the count cell of each particle in its contiguous block. One thread then sorts a strided sample of about 64 cells per thread and splits the cells at its quantiles, so each owner gets about the same number of particles. Every thread counts its block's particles per owner and, after a prefix sum, moves the cells to their owners' contiguous segments. Each owner then increments its own cells. The counts are integers, so the result does not depend on the order of the additions. It equals the serial count exactly while no cell holds more than $2^{24}$ particles, the largest integer range of `float`. Above that, the serial and earlier atomic counts were not exact either. Earlier revisions incremented the shared grid with `#pragma omp atomic`. Particles cluster near their sources, so threads contended for the same cells: on `hhcpu`, concentration took 0.79 s with 56 threads against 0.29 s serially at 1,000,000 particles/hour ([backend matrix](backend-matrix-evaluation.md)). The partition uses two uninitialized particle-sized pointer arrays, 16 bytes per particle, first touched by the threads that use them. Builds without OpenMP, and OpenMP runs on one thread, keep the direct serial loop. A component benchmark on one `hhcpu` node (job 1077714, GCC 12, `OMP_PLACES=cores`, `OMP_PROC_BIND=spread`) took the occupancy measured in the 14:00 Sarno output at 1,000,000 particles/hour: 3.49 million particles in 20 cells, 56.5% of them in one cell. There, one evaluation took 0.13 s on 14 threads and 0.19 s on 56 with the atomic update, against 0.011–0.013 s and 0.009–0.011 s now. With 5.3 million particles spread over thousands of cells, the atomic update has little contention and remains faster at 56 threads (6 ms against 11 ms); the two are equal at 14. Every benchmark count equalled the atomic count in every cell. The benchmark times the counting alone; `EVALUATE sec:` also includes the land-mask pass. In the full Sarno run, `EVALUATE sec:` summed over the five intervals fell from 0.79 s to 0.07 s for OpenMP 1×56 and from 0.48 s to 0.09 s for MPI+OpenMP 16×14 at 1,000,000 particles/hour ([reruns](backend-matrix-evaluation.md#reruns-after-the-first-improvements)). CUDA copies optional normalized WRF wind and WW3 Stokes arrays alongside the ocean window and passes null fields only when the corresponding adapter is disabled. Allocations, transfers, launches, synchronization, events and releases are checked for runtime errors. Host reads synchronize after asynchronous device copies, and per-thread event timings are stored independently before aggregation.

Within one process, the OpenMP particle loop uses dynamic scheduling in chunks of 64 particles. Work per particle is uneven within a solver interval: particles emitted during the interval move only from their emission time, and stranded or dead particles stop early. Contiguous equal-count partitions therefore left the thread holding the newest particles idle while others finished. Each update reads only its own particle state and identity-keyed counter-based random numbers, so the schedule changes neither trajectories nor stochastic draws; CTest checks this exactly against serial execution. With CUDA, a process copies the forcing window to each visible device once per interval, then moves its local particles as one contiguous section per device: one asynchronous upload, kernel launch, and download on a dedicated stream for each GPU, launched on every device before waiting on any. Earlier code launched a separate kernel from every OpenMP thread for each device and synchronized the whole device after each launch, so device time grew with the host thread count. Particle packing and unpacking around the device copy run as OpenMP loops. The land mask of gridded concentration output is applied from a list of land cells built once per forcing window rather than by testing the two-dimensional mask in every vertical level at every interval; the written values are unchanged.

MPI transfers the fixed-width particle identity, six double-precision state fields, 16-bit object identifier, and 8-bit crosswind orientation through one shared derived datatype definition whose resized extent equals the complete particle structure. Rank 0 distributes the particles of each solver interval in an interleaved decomposition. Particles are stored in emission order, so the oldest integrate the whole interval and the newest only its remainder. Contiguous blocks, used before this revision with the remainder on rank 0, therefore gave the first ranks the most work. At two ranks on `hhcpu` the solver reached 83% efficiency, against 100% for two OpenMP threads ([backend matrix](backend-matrix-evaluation.md)). With $N$ particles on $P$ ranks, particle $q$ now goes to rank $r=q \bmod P$. Rank $r$ receives $n_r=\lfloor N/P\rfloor+[r<N \bmod P]$ particles, where $[\cdot]$ is 1 when its condition holds and 0 otherwise. They form a contiguous block of the send buffer starting at $o_r=r\lfloor N/P\rfloor+\min(r, N \bmod P)$, with particle $q$ in slot $o_r+\lfloor q/P\rfloor$. After the gather, rank 0 reads each particle back from the same slot, so the particle vector, concentration evaluation, and outputs keep the emission order. Each update depends only on the particle's own state and identity-keyed random numbers, so results are bit-identical for every $P$. Interleaving balances emission age, not every cost. A periodic pattern whose period divides $P$ still lands on one rank: with two sources emitting alternately on two ranks, each rank gets one source, and particles stranded early cost less. The FlexMPI/EMPI path uses the same decomposition. Packing the send buffer, unpacking the received block into the rank's particles, packing them back, and the final rank-0 unpacking all run as OpenMP loops. Each rank fills its local particles by copying one particle and then setting the copies' states. Constructing every particle from its state instead would look up its logger under the log4cplus hierarchy lock, which serializes the loop. On rank 0, `DISTRIBUTE sec:` logs the time from packing to the filled local particles, which includes the scatter. `COLLECT sec:` logs the time from packing the moved particles to the restored emission order, which includes the gather and so the wait for the slowest rank. Rank 0 also logs the phases outside the solver interval, all in seconds of wall time. `FORCING sec: a max: b` is the preparation of one forcing window: reading, normalization, the appended boundary record, and regridding. `a` is rank 0's time and `b` the slowest rank's, found with one `MPI_Reduce` per window; the solver interval's opening barrier waits for that rank. A window already read as the adjacent one costs almost nothing. `SETUP sec:` covers sources, saved input, and restart loading for the window. `OUTPUT sec:` is the output section after the solver intervals: the writes themselves, or with `io.async=true` the particle snapshots and queueing, including any wait for a full queue. `FLUSH sec:` is the final wait for queued writes, and `RUN sec:` the whole run from configuration of the output writer to the last published output. Process start, MPI initialization, and configuration parsing lie outside `RUN sec:`. None of these timers changes the computation. The MPI regression packs and unpacks with the same slots on 2, 3, and 4 ranks (`mpi_decomposition_parity`, `mpi_decomposition_parity_3_ranks`, `mpi_decomposition_parity_4_ranks`), leaving remainders of 1–3 particles. It alternates particles released at the interval start with particles released at 30 s, verifies lossless scatter/gather ordering including drift metadata, and compares the distributed seeded update with serial execution. On `hhcpu`, MPI 2×1 efficiency on the Sarno workload rose from 83.4% to 99.3%, and 4×1 reached 98.8% ([reruns](backend-matrix-evaluation.md#reruns-after-the-first-improvements)).

The decomposition regression also updates each rank's particles with OpenMP dynamic scheduling when OpenMP is enabled. CTest checks one rank and one thread, and two ranks with two threads each, against the same serial seeded reference. It checks every particle's identity, grid position, health, age, time, and drift metadata exactly. This verifies the selected synthetic update and scheduling independence; it does not establish equivalence for every forcing field or establish observational validity. Run `ctest --test-dir build -R 'mpi_(decomposition|openmp).*parity|cuda_particle_parity' --output-on-failure` after configuring `USE_MPI=ON`, `USE_OMP=ON`, and `USE_CUDA=ON`. CUDA parity requires an accessible device; a skipped result is compile-only evidence.

Fast CI compiles serial, OpenMP, MPI, and combined MPI/OpenMP application configurations. Scheduled validation compiles MPI, OpenMP, and CUDA together, tests OpenACC, and runs every CPU-side regression, including MPI execution. The CUDA regression compares deterministic, seeded-stochastic, dynamic-WRF, and coupled WRF/WW3 CPU/GPU state and skips only when a device is absent. The manual GPU workflow runs it on a labeled self-hosted NVIDIA runner; the FlexMPI workflow requires an installation providing the actual EMPI runtime. Compile-only accelerator results are not numerical parity evidence.

The `gn03` Slurm parity run used one V100, one MPI task, and one OpenMP thread. It verified the CPU/CUDA particle update on the synthetic regression fields after aligning the east–west metric and environmental interpolation order. It does not compare complete application NetCDF outputs or establish four-way equivalence for every rank/thread/GPU count.

Rank 0 gathers the particles and writes every history and gridded file. With `io.async=true` it hands each output to one background writer thread and continues with the next forcing window; NetCDF writes overlap particle integration and concentration evaluation but not forcing reads, because NetCDF-C and HDF5 calls are serialized process-wide. The writer never calls MPI, and MPI builds request `MPI_THREAD_FUNNELED`. Parallel file system options (atomic publication, `fsync`, node-local staging, and Lustre striping) are described in [output publication](io.md). With `io.parallel_write="collective"`, in builds with MPI and parallel NetCDF, rank 0 instead scatters each output in contiguous particle or `eta_rho` blocks and every rank writes its block with MPI-IO or parallel NetCDF-4 in collective mode ([collective writes](io.md#collective-writes)); the solver's per-interval gather to rank 0 is unchanged.

## Resource limits

Two checks stop a run that would otherwise fail without a WaComM++ message. Both live in `ResourceLimits.hpp` and are covered by the `resource_limits` test.

**Particle count.** The solver interval, the MPI scatter/gather counts and displacements (`int` in MPI-3), and the run-loop counter use `int`. Earlier revisions assigned `particles->size()` to `int` and cast the per-rank counts with `(int)`, which truncated silently above $2^{31}-1=2\,147\,483\,647$ particles. For example, 1,000,000 particles per hour sustained for 90 days gives $2.16\times10^9$. Rank 0 now checks the total before packing each interval and stops with an error that names the count and the `INT_MAX` limit. Every count and displacement is bounded by that total, so it fits too. MPI-4 large-count collectives (`MPI_Scatterv_c`) are not used, because Open MPI 4.1, used on `hhcpu`, does not provide them.

**Forcing memory.** Every rank holds its own copy of the normalized ocean forcing. Before any field is read, world rank 0 reads the header of the first window in the tracking direction through the adapter's `dimensions()` and estimates the resident forcing of one rank:

$$
B_\mathrm{rank}=B_w(T+1)+B_w(T),\qquad
B_w(R)=4R\,N_\eta N_\xi\,(2N_\rho+2N_w+1)+48\,N_\eta N_\xi+8\,(R+N_\rho+2N_w).
$$

Here $B$ is in bytes, $T$ is the number of time records in a window, $N_\rho$ and $N_w$ are the `s_rho` and `s_w` level counts, and $N_\eta N_\xi$ is the number of horizontal rho points. The first term counts `u`, `v`, `w`, `AKt`, and `zeta` as `float`. The second counts the six two-dimensional `double` grids (`h`, mask, longitude, latitude, and their radian copies), and the third counts the `double` axes. The active window carries one appended boundary record, and the adjacent window is held while that record is appended. With a single input, $B_\mathrm{rank}=B_w(T)$. The estimate leaves out particles, the concentration grid, transient adapter read buffers, and WRF and WW3 fields. For the Sarno native forcing ($T=2$, $N_\rho=30$, $N_w=31$, $1135\times1528$ points) it gives 4.13 GiB, against a measured peak resident set of 3.8–5.1 GiB per rank on `hhcpu` ([backend matrix](backend-matrix-evaluation.md)).

The first rank of each node, found with `MPI_Comm_split_type(MPI_COMM_TYPE_SHARED)`, multiplies $B_\mathrm{rank}$ by the ranks on its node. It compares that product with the tightest limit it can see: the cgroup v2 `memory.max` or cgroup v1 `memory.limit_in_bytes` of its cgroup and every ancestor, read from `/proc/self/cgroup`, and `MemAvailable` from `/proc/meminfo`. Above 80% of the limit it logs a warning. Above 100%, with `simulation.memory_check="error"` (the default), every rank stops before reading forcing, and the log names the estimate, the limit, and its source. `"warn"` only logs, and `"off"` skips the check. Where no limit is visible, as on macOS and Windows, the check only logs the estimate. For example, 28 Sarno ranks need an estimated 115.6 GiB, so under the 56 GiB default `hhcpu` grant they now stop with this message instead of being killed with exit code 137. Four ranks (16.5 GiB) pass. The check changes neither physics nor outputs. It does not apply when the forcing cannot be opened: the adapter then reports its own validation error. Any error that stops a run, including this one, is logged at `ERROR` level by every rank that raises it, as `rank: message`, before the run exits with status 1 (`MPI_Abort` in MPI builds). Console output is written unbuffered (`std::unitbuf`), so the last lines also survive a job that the scheduler kills. Earlier, the uncaught exception terminated the process, and the buffered log lost the message: on `hhcpu`, only the bare exception text reached standard error.

Record ranks, threads, affinity, GPU and driver data with results. Validate deterministic output against serial execution before scientific use.

The [two-process Sarno Slurm example](../examples/wacomm-sarno-lite/docs/README.md#two-process-mpi-calculation) runs the six-hour seeded ROMS calculation on `high-wn` with OpenMP/CUDA disabled. `bash examples/wacomm-sarno-lite/tools/run_sarno_lite.sh --mpi` requests two cores on one node and uses OpenMPI with explicit core binding. Its five particle snapshots match the serial run exactly after identity ordering; this evidence covers the documented case and excludes inter-node communication performance and observational validation.

The [MPI/OpenMP Sarno sweep](../examples/wacomm-sarno-lite/docs/README.md#mpiopenmp-strong-scaling) fixes the six-hour scientific workload and varies MPI ranks over 1, 2, 4, 8, 16, and 32. OpenMP is compiled in, with `OMP_NUM_THREADS=1`, `OMP_THREAD_LIMIT=1`, dynamic teams disabled, and core binding. CUDA is disabled. Each job exclusively reserves the same `high-wn` node, and dependencies serialize the sweep. The plotted efficiency divides by active ranks; it is not utilization of all 32 reserved cores. Primary timings sum rank-zero solver intervals bracketed by MPI barriers, excluding forcing download, preparation, loading, and file writes; they include scatter/gather and rank-zero concentration work. A secondary series measures complete application elapsed time with native reads and writes. Neither series is isolated particle-kernel or multi-thread performance. Preparation runs separately with one process. Serial work limits strong scaling (Amdahl, 1967); the experiment does not fit a serial fraction or separate I/O, memory-bandwidth, and communication costs.

The [OpenMP Sarno sweep](../examples/wacomm-sarno-lite/docs/README.md#openmp-strong-scaling-and-mpi-comparison) uses one MPI process with 1–32 OpenMP threads. Slurm allocates `--cpus-per-task=N`; OpenMPI binds its single process to `N` cores using `--map-by slot:PE=N --bind-to core`. `OMP_PROC_BIND=SPREAD`, `OMP_PLACES=cores`, fixed thread count, and disabled dynamic teams keep workers inside that allocation. This avoids confining all OpenMP workers to a single MPI-bound core. Affinity logs record the actual placement. Threads share environmental arrays and parallelize concentration/mask work, whereas the preceding one-thread-per-rank MPI sweep replicates arrays and uses scatter/gather. Compare the separately normalized ratios and absolute times; a single historical sweep cannot establish a causal bottleneck or universal backend ranking.

The [shared performance-evaluation protocol](performance-evaluation.md) defines the required CPU/GPU sweeps, validation evidence, plots, and per-run Codex notes for every runnable example. Historical Sarno figures use their separately documented protocol.

The [Sarno shared-protocol workflow](../examples/wacomm-sarno-lite/docs/performance-evaluation.md) exercises the full MPI/OpenMP/hybrid matrix and selected-CPU GPU sweep on the same six-hour scientific workload. Its CUDA-capable executable is used for both CPU-hidden and GPU-visible runs; every point requires numerical equivalence before performance interpretation. Multi-node MPI launchers must explicitly export `CUDA_VISIBLE_DEVICES` and `OMP_*` settings to remote ranks and archive each rank’s observed device binding; a batch-shell setting alone did not propagate in the Sarno 64-process pilot and caused remote ranks to enter the GPU path.
