# Reproducible example and performance contract

Every checked-in example is a scientific interface to the one WaComM++ model. Keep its configuration and Markdown guide paired. The guide states the scientific question, field identities and units, complete configuration role, exact command, expected output, numerical verification and tolerance, limitations, interpretation, reproducibility metadata, and a `References` section with verified peer-reviewed support. An example name is not a physics switch. Preserve forward/backward, stochastic, and restart semantics of the core.

Place example-specific launchers, data preparation, collectors, checks, and tests in `examples/<example>/tools/`. Place example-specific protocol, results, captions, schemas, and other documentation in `examples/<example>/docs/`; place versioned figures below that `docs/` directory. A configuration-paired guide may be a root `README.md` or `docs/README.md`; the Sarno Lite guide and all its related documents belong only in `examples/wacomm-sarno-lite/docs/`. Put only scientifically and technically reusable processing in repository `tools/`. A reusable processor takes paths and declared metadata as inputs and must not infer a product, coordinate system, calendar, seed, tolerance, or workload from a filename.

Use [`docs/performance-evaluation.md`](../docs/performance-evaluation.md) for fixed-workload CPU/MPI/OpenMP/hybrid and selected-CPU GPU performance experiments. Follow its declared MPI-only, OpenMP-only, fixed-worker hybrid, and device sweeps without changing scientific inputs within a sweep. For a problem-size experiment, declare the varied scientific quantity, units, and values, keep all other physical inputs and random seeds fixed, and use a separate baseline and speedup denominator for each size. Do not pool runs across particle counts, builds, nodes of different types, forcing revisions, timing scopes, or backend-equivalence policies. Randomize or rotate configuration order across at least three independent replicate blocks after a documented warm-up. Record every raw sample and run order; do not impute missing results or suppress failed cases.

A point is eligible for a performance chart only after successful execution, positive finite complete timing intervals, verified MPI/OpenMP/device counts and bindings, and particle and gridded-output comparison against the appropriate same-workload reference by stable particle ID and physical time. State exact or bounded numerical tolerances and their units. Verify CPU/GPU backend equivalence; timing similarity is not physics validation. A failed point remains archived with a Codex-ready Markdown review note, but is excluded from valid speedup and efficiency curves. Every valid resource configuration also gets a review note with the run record, hashes, raw samples, validation evidence, and instructions to seek generic core or example-infrastructure improvements rather than workload-specific physics shortcuts.

When a scheduler delay leaves a matrix incomplete, retain successful raw samples and allow a clearly labeled provisional diagnostic. Its note must identify the missing tuples, checked and unchecked scientific comparisons, and the exact reason no final speedup curve, CPU selection, or GPU recommendation can be made. The final collector must independently verify the complete matrix before replacing provisional evidence.

For each suite archive the Git revision and working changes, complete resolved configuration, source/forcing/restart/executable/output checksums, seed, compiler/CMake/dependency versions, platform and node topology, MPI/OpenMP/GPU bindings, scheduler IDs, raw stdout/stderr, timer scope, per-run sample order, numerical tolerances, validation reports, and figure-generation environment. Use immutable run roots; never overwrite a previous scientific result. Version a compact results table, chart files, descriptive alternative text, and a caption that identifies a diagnostic measurement rather than observational validation. Keep large forcing and simulation output outside Git and state where its archive lives. Document unavailable hardware or failed scientific checks explicitly rather than fabricating a complete matrix.

Any model-core optimization motivated by an example must preserve the common equations and run the relevant portable, serial, MPI, OpenMP, CUDA, forward/backward, stochastic, and restart checks. Update the model, configuration, reference, main README, and relevant example documents whenever the implementation or user-visible behavior changes. A performance gain for one use case is insufficient evidence for a generic change.
